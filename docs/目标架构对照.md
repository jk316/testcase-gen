# 目标架构 vs 现状 · 对照文档

> 目标：输入一条**结构化测试需求**（可含并发混合攻击 + 业务流量），输出**API 粒度、可执行、参数依赖闭环**的测试步骤序列。
> 用途：`refactor` 阶段对齐用。左栏「现状」、右栏「目标」，末节给出改造优先级。
> 配套：现状整体描述见 [`项目总结.md`](./项目总结.md)，本文只聚焦「差距」。

---

## 0. 需求语义（已确认，作为输入模型的事实基准）

| 语义 | 定义 |
|------|------|
| 混合攻击 | **并发**：多种攻击类型同时发起，不是顺序执行 |
| 攻击总带宽 | 所有攻击流共享的总带宽（例：1Gbps） |
| 业务总带宽 | 合法业务（背景）流量的总带宽，与攻击流**独立说明** |
| 带宽分配 | 混合时**平均分配**：攻击总带宽 ÷ 攻击种类数；业务总带宽 ÷ 业务种类数 |
| 输出粒度 | API 级步骤（每步 = 一个具体 API 调用 + 参数 + 依赖），非"登录/发流"粗粒度 |

> 隐含的关键推论：**「并发」不是多个并行 run 步骤，而是 N 个攻击/业务 profile 配置步骤「扇形汇入」一个 run 步骤**（见 §3）。因此输出仍是线性步骤序列，但参数依赖图存在 fan-in。

---

## 1. 输入需求模型

| | 现状 | 目标 |
|---|---|---|
| 输入载体 | `inputs/intent.txt` 纯文本，一行一个意图，无结构 | 结构化 schema（JSON），机器可校验 |
| 攻击类型 | 单句自由文本，无列表概念 | `attack.types: [udp_flood, http_get_flood, ...]`，多类型支持 |
| 带宽 | 藏在文本里，靠 LLM 自己读 | `attack.total_bandwidth_mbps` 与 `business.total_bandwidth_mbps` 两个独立字段 |
| 时长 | 同上 | `duration_sec` |
| 目标 | 同上，UDP 目的 IP 与 HTTP URL 混在一个字段 | 按攻击类型分别表达 `targets: {udp_flood: {dest_ip}, http_get_flood: {url}}` |
| 分配规则 | 无 | 显式 `allocation: equal`（均分），由**代码**算出每种攻击带宽，不交给 LLM 心算 |

**目标输入草案：**

```json
{
  "test_name": "UDP+HTTP GET 并发混合攻击",
  "duration_sec": 200,
  "attack": {
    "total_bandwidth_mbps": 1000,
    "allocation": "equal",
    "types": ["udp_flood", "http_get_flood"]
  },
  "business": {
    "total_bandwidth_mbps": 2000,
    "allocation": "equal",
    "types": ["http_browse"]
  },
  "targets": {
    "udp_flood": { "dest_ip": "11.0.0.1/24" },
    "http_get_flood": { "url": "http://example.com/index.html" }
  }
}
```

> 带宽均分（1000 ÷ 2 = 各 500Mbps）应在**进入 LLM 之前**由确定性代码完成，LLM 只负责"填哪个 API 参数"，不负责"算数"。

## 2. 意图 → API 映射（检索）

| | 现状 | 目标 |
|---|---|---|
| 实现 | `generate_steps_node` 用 `load_api_capabilities()` 读全量 503 条 `api_descriptions.jsonl`，**整段塞进 prompt** | 接入已实现的 `ApiIntentIndexNew.search`（FAISS 召回 50 → CrossEncoder 精排 10 → LLM 重排 3） |
| 问题 | token 浪费、易选错 API、且与"已造好的检索器"割裂 | 每个攻击类型先检索出候选 API，再让 LLM 从候选里挑 |
| 影响 | 这是「选对 API」这一核心环节，当前等于没做检索 | 混合攻击要按攻击类型分别检索，检索结果作为步骤编排的输入 |

---

## 3. 步骤编排（并发混合攻击）

| | 现状 | 目标 |
|---|---|---|
| 模板 | 固定 `login → … → logout` 单线模板（`steps.txt` 硬编码 12 步） | 由「攻击类型 × 并发结构」驱动编排 |
| 并发表达 | 无 | N 个攻击/业务 profile 配置步骤 **fan-in 到 1 个 run 步骤**（设备端并发由单次 `testcase/run` 实现） |
| 共享资源 | 隐式（session_id 靠经验池/LLM 猜） | 显式建模：会话、预留端口、模板 id 作为跨步骤共享资源 |
| 带宽分配 | 无 | 编排前由代码均分，写入各 profile 步骤参数 |

**目标编排形状（示意）：**

```
login ──> port/reserve ─┬─> attack.flow/profile.create (UDP flood, 500Mbps)
                        ├─> attack.flow/profile.create (HTTP GET flood, 500Mbps)
                        └─> business.profile.create (HTTP browse, 2000Mbps)
                                        │
                                        ▼
                              testcase/create ──> testcase/run (200s)
                                        │
                              stats/model ──> logout
```

## 4. 参数依赖推理

| | 现状 | 目标 |
|---|---|---|
| 判断方式 | `params_reasoning_node` 让 LLM 判断 `from_previous_step` / `generated` | 保留 LLM 判断，但加**确定性闭环校验** |
| 校验 | **无**：`source_output_field` 是否真存在于前序步骤 output，代码从不验证 | 校验 `source_step_id` / `source_output_field` 存在性，失败即修正或报错 |
| 混合攻击风险 | 跨攻击复用 session_id/端口/模板 id 时最容易错填 | 共享资源用显式引用，禁止 LLM 凭空捏造 `generated` 值（除非命中经验池规则） |

---

## 5. 输出与校验

| | 现状 | 目标 |
|---|---|---|
| 校验 | `finalize_testcase_node` 直接 `save_json_file`，**没走** `models/` 的 Pydantic 模型（README 声称 `strict=True` 但实际未接） | 每步用 Pydantic `model_validate_json(strict=True)` 校验结构 |
| 合并结构 | `{name, demand, tester, steps}` 扁平顺序列表 | 增加并发/fan-in 表达（如 run 步骤的 input 引用多个 profile 产出），或至少保证依赖图可还原 |

---

## 6. 循环控制（多意图 / 多步骤）

| | 现状 | 目标 |
|---|---|---|
| 步骤级循环 | ✅ 已接（`loop_control_step` → `should_continue_step`） | 保留 |
| 意图级循环 | ❌ `loop_control_intent` / `should_continue_intent` 已注册但**未连边**，只跑 intent.txt 第一条 | 接通，逐意图产出独立 merged_testcase |
| 跳过步骤 | ❌ 崩溃：`generate_testcase_node.py:64` 空 `candidate_api_ids` 时 for 循环体不执行、函数无兜底 `return`（隐式 `None`）→ `params_reasoning_node.py:29` 抛 `IndexError` | 空候选步骤显式返回占位/跳过，下游同步跳过 |

> 实测：UDP flood 意图生成 22 步，其中 18/19/20 为「跳过说明」步，跑到第 18 步就 `IndexError` 中止，`merge_testcase` 未执行。

## 7. 基础设施（Redis 参数索引）

| | 现状 | 目标 |
|---|---|---|
| 配置 | `config.py` `remote_host="10.99.80.159"` 写死，本地不可达时慢超时 | 配置外置（env），加 `socket_connect_timeout` 快速失败 |
| 就绪校验 | 无：索引没建就空参数降级，且无提示 | 启动时校验索引是否就绪，缺失时给出明确指引（离线 `build_api_index_redis.py`） |

---

## 8. 工程性

| | 现状 | 目标 |
|---|---|---|
| LLM 调用 | 单意图 22 步 ≈ 66+ 次**串行**调用，无缓存/批处理/重试隔离 | 相同（api_id, 参数）的结果缓存；可并行的步骤并行；失败重试与降级 |
| 输出治理 | `outputs/` 堆几十个历史 json/jsonl，中间产物与最终产物混放 | 分目录/带版本、每次运行隔离输出、旧产物清理策略 |
| 评测 | 无 | 建立评测集：API 命中率、参数依赖正确率、可执行率（见 `项目总结.md` §四） |

---

## 9. 改造优先级（建议顺序）

1. **P0 正确性**：修跳过步骤崩溃（§6）+ 输出接 Pydantic 校验（§5）——不修则跑不完、产出不可信。
2. **P0 需求建模**：定义结构化输入 schema + 带宽均分的确定性计算（§1、§3）——这是"混合攻击"目标成立的前提。
3. **P1 检索接入**：把 `ApiIntentIndexNew.search` 接进"意图→候选 API"（§2）——替换全量塞 prompt。
4. **P1 参数闭环**：`from_previous_step` 字段存在性校验 + 共享资源显式引用（§4）。
5. **P2 循环与基础设施**：接通意图级循环、Redis 配置外置与就绪校验（§6、§7）。
6. **P2 工程化**：缓存/并行/输出治理/评测基线（§8）。
