# testcase-gen 项目总结

> 面向**信而泰（Xinertel）网络测试仪**的 **AI 自动生成测试用例**系统。
> 输入一句测试意图（如「测试 UDP flood 攻击，峰值 500Mbps、时长 60 秒、目的 IP 11.0.0.1/24」），
> 系统自动检索相关 API、规划测试步骤、推理参数依赖，最终输出可直接执行的、结构化的测试用例 JSON。

---

## 一、项目背景与要解决的问题

人工编写网络测试仪测试用例存在三个痛点：

1. **门槛高**：需要熟悉信而泰大量 OpenAPI（本项目覆盖 503 个 API 路径）及其参数细节；
2. **效率低**：从需求文档到可执行用例，需要逐条查阅 API、手工编排步骤、人工补全参数依赖；
3. **易出错**：多步骤用例中，后一步的参数往往依赖前一步的输出（如 login 返回的 token），人工传递容易漏填、错填。

本项目的目标是把「测试意图 → 可执行测试用例」这条链路**自动化**，让非专家也能快速产出高质量用例。

---

## 二、整体方案：三阶段流水线

核心是一条 **「意图 → 步骤 → 用例」三阶段流水线**，由 LangGraph 状态机编排：

```
intent（测试意图） → steps（粗粒度步骤计划） → testcase（细粒度可执行用例）
```

**LangGraph 节点链路**（对应 `state.py`）：

```
load_intent_list → generate_steps → generate_testcase → params_reasoning
                 → finalize_testcase → merge_testcase → 输出用例 JSON
                        ↑___________________|
                     （步骤循环：下一 step 回到 generate_testcase）
```

架构图见 `testcase-gen-architecture.html`（同目录，浏览器打开即可交互查看）。

### 分层结构

| 层 | 组成 | 说明 |
|----|------|------|
| 输入层 | 需求文档 docx、测试意图 intent.txt | 需求经 `split.py` 按标题层级拆分为测试意图 |
| 编排层 | 6 个 LangGraph 节点 | 状态机 + 条件边 + 步骤循环（`astream` 异步执行） |
| 支撑层 | RAG 检索、Redis 参数索引、经验池、LLM | 为编排层提供 API 召回、参数、历史经验与模型能力 |
| 输出层 | `merged_testcase/*.json` | `{name, demand, tester, steps}` 结构 |

## 三、主要工作

### 1. 需求文档解析（`utils/split.py`）
用 python-docx 读取需求文档，按「章标题 / 一级条标题 / 二级条标题 / 三级条标题」样式递归拆分，产出树状结构化 JSON。

### 2. DDoS 攻击类型识别与去重（`utils/is_ddos.py`）
用 LLM 从需求内容中匹配 **78 种已知攻击类型**（`inputs/known_xinertel_attacks.md`），严格规则防止「拒绝服务攻击 → 具体类型」的过度推断，并做去重汇总。

### 3. LangGraph 编排（`state.py` + `nodes/`）
- 用 `StateGraph` 定义状态机，`TypedDict` 定义状态字段（`schemas/state.py`）；
- 条件边实现步骤循环，`recursion_limit` 控制执行深度；
- 异步 `astream` 流式执行，日志记录每次节点迭代。

### 4. API 语义检索 RAG（`utils/api_intent_index_new.py`）
- LLM 为每个 OpenAPI path 生成一句语义描述，embedding 后建 FAISS 向量索引；
- **三级漏斗检索：FAISS 向量召回(50) → CrossEncoder 精排(10) → LLM 重排(3)**。

### 5. API 参数正向索引（`utils/build_api_index_redis.py` + `extract_api_params.py`）
- 从 OpenAPI 定义**递归展开 `$ref`、数组、嵌套对象**，提取每个 API 的输入/输出参数；
- 存 Redis Hash，key 格式 `api:params:<METHOD>:<PATH>`，构建与查询分离。

### 6. 参数依赖推理（`nodes/params_reasoning_node.py`）
判断每个 `input` 参数是**来源于前序步骤的 output**（`from_previous_step`），还是**本步骤新生成值**（`generated`），并参考经验池知识。

### 7. 经验池（`schemas/experience_pool.py`）
记录「意图 → 检索到的 API 映射」，人类校验后（`pending → confirmed`）参与后续检索，用余弦相似度命中历史相似意图。

### 8. 用例规范化与合并（`finalize_testcase` + `merge_testcase`）
按标准格式规范化每个 step，最终合并为 `{name, demand, tester, steps}` 结构。

## 四、量化指标 / 效果

以下指标均来自仓库实际数据（可复核）：

| 指标 | 数值 | 数据来源 |
|------|------|----------|
| 覆盖 API 路径数 | **503 个** | `inputs/xrt_openapi.jsonl` 中 `paths.*` 计数 |
| 数据模型 / 对象定义 | **1596 个** | 同文件中 `definitions.*` 计数 |
| API 语义描述 | **503 条**（100% 覆盖） | `outputs/api_descriptions.jsonl` 行数 |
| 提取的 API 参数 | **4678 条** | `outputs/api_params.jsonl` 行数（含递归展开 `$ref`/数组/嵌套） |
| 已知 DDoS 攻击类型 | **78 种** | `inputs/known_xinertel_attacks.md` |
| 经验池记录 | **61 条** | `outputs/experience_pool.jsonl` 行数 |
| 检索漏斗 | **50 → 10 → 3** | RAG 三级检索（召回→精排→重排） |
| LLM 可插拔 | **3 家**（通义 qwen-plus / 智谱 glm-4.7 / DeepSeek） | `config.py`，失败回退通义 |

### 待补充的评测指标（当前仓库无对应评测数据）

以下指标需要补充评测集或人工评审记录后才能给出数值，建议后续补测：

- **端到端用例生成准确率 / 可执行率**（生成用例中可直接在测试仪上执行的比例）；
- **步骤规划 API 命中率**（规划步骤命中的候选 API 是否含正确 API，Top-3 命中率）；
- **参数依赖推理正确率**（`from_previous_step` / `generated` 判断的准确率）；
- **相对人工的效率提升**（生成单条用例的耗时对比、需求→用例的自动化覆盖率）。

## 五、不足与后续规划（如实说明）

1. **RAG 检索链尚未接线主图**：`api_intent_index_new.search` 三级检索已实现，但主流程 `generate_steps` 目前仍用静态读全量 `api_descriptions.jsonl` 的方式，尚未切换到 FAISS→CrossEncoder→LLM 检索链。
2. **意图级循环未接线**：`state.py` 中 `loop_control_intent` / `should_continue_intent` 两个节点已注册但未连入边，当前主图仅实现了「步骤级循环」，多意图批量循环尚未打通。
3. **缺少评测体系**：暂无端到端准确率、命中率、推理正确率的自动化评测，效果难以量化对比。
4. **后续方向**：接通 RAG 检索链与意图循环；建立评测集与回归基线；经验池人工校验流程线上化。
