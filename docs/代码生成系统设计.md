# 信而泰测试代码生成系统 · 设计文档

> 目标：输入**需求文档（docx）**与**测试意图（intent.txt）**，输出一份**可直接运行的信而泰 Python 接口代码**（形如 `examples/testcode_examples.py`）。
> 本文是全新设计，不依赖旧的三阶段 JSON 流水线。中间过程按"代码生成"这一目标重新设计。

---

## 1. 目标与边界

**输入**
- `*.docx` 需求文档：非结构化，可能含多条测试需求。
- `intent.txt` 测试意图：一条或多条精简意图，可人工补充或作为 docx 拆分结果的产物。

**输出**

- 一个 `.py` 文件（如 `generated_testcase_udp_http_mixed.py`），**可直接 `python xxx.py` 执行**，驱动信而泰测试仪完成整条测试流程。

**明确不做 / 不再做**

- 不输出"测试用例 JSON 描述"（描述无法自证可执行）。
- 不维护一条固定模板流水线（旧 `login→…→logout` 硬编码步骤作废）。

**核心假设**（需求语义，已确认）

- 混合攻击 = **并发**；攻击总带宽与业务总带宽是两个独立量；混合时**平均分配**带宽。

---

## 2. 三条核心设计决策

### 决策 1：输出"代码"而非"描述"，因为代码可自证
生成 JSON 用例，好坏只能靠人看；生成 Python 代码，好坏可以**直接运行**来验证。执行成功 = 用例有效，这是天然的验收标准，也是评测指标（可执行率）能被自动化度量的前提。

### 决策 2：稳定的 SDK 运行时 + 生成的"薄"脚本
绝不每次让 LLM 从零写整套客户端代码。分层：

```
[稳定层]  AlpsClient + 领域模型(models/ddos_attack_config.py)   —— 手写、测试过、版本化
[生成层]  generated_xxx.py                                       —— 只 import 稳定层，编排调用顺序
```

生成层只管"调什么、按什么顺序、传什么参数"，底层 HTTP/签名/模型全部复用稳定层。LLM 永远不碰稳定层，可靠性被钉死。

### 决策 3：LLM 只做"理解"，代码只做"确定性工程"

- **LLM 负责**：docx→结构化需求抽取、意图→测试计划编排、API 检索重排、模糊目标解析。
- **确定性代码负责**：带宽均分、schema 校验、模板渲染、依赖检查、代码组装。

凡是能算的（带宽 ÷ 种类数）、能校验的（引用的字段是否存在）、能模板化的（脚本骨架），都不交给 LLM。

---

## 3. 总体架构

```
              docx ──┐
                     ├──► ① 需求解析 ──► [TestRequirement ...]   (结构化需求)
         intent.txt ─┘
                                     │
                                     ▼
                      ② 意图理解（LLM + 检索 + 确定性编排）
                                     │
                                     ▼
                             ③ TestPlan（中间表示 IR）
                                     │
                                     ▼
                      ④ 代码合成（模板渲染，确定性）
                                     │
                                     ▼
                             ⑤ 校验与执行（静态 → 运行）
                                     │
                                     ▼
                        generated_xxx.py（可执行）
```

分五层，每层职责单一、可独立测试。

## 4. 中间表示 IR（设计的核心）

系统内部不直接"文档→代码"，而是"文档→**IR**→代码"。IR 分两级。

### 4.1 结构化需求 `TestRequirement`（输入模型）

由需求解析层产出，字段机器可校验：

```python
@dataclass(frozen=True)
class AttackSpec:
    type: str                  # "udp_flood" | "http_get_flood" | ...
    bandwidth_mbps: int        # 均分后的带宽（确定性代码算出）
    target: dict               # 按类型：{"dest_ip": "11.0.0.1/24"} 或 {"url": "..."}
    params: dict               # 其它攻击参数

@dataclass(frozen=True)
class BusinessSpec:
    type: str
    bandwidth_mbps: int        # 均分后的带宽
    params: dict

@dataclass(frozen=True)
class TestRequirement:
    name: str
    duration_sec: int
    attacks: list[AttackSpec]      # 并发攻击，已均分带宽
    businesses: list[BusinessSpec] # 合法业务流，已均分带宽
    base_url: str
    username: str
    password: str
```

**带宽均分在此层用确定性代码完成**：`attack.total_bandwidth // len(attacks)`，不让 LLM 心算。

### 4.2 测试计划 `TestPlan`（编排 IR）

意图理解层的产出，是"代码合成"的直接输入。它是一组**操作步骤 + 参数 + 依赖**：

```python
@dataclass(frozen=True)
class Ref:                       # 参数依赖：引用前面步骤的产出
    step: str
    field: str

@dataclass(frozen=True)
class PlanStep:
    step_id: str                 # 唯一，如 "login" / "create_flow_udp_flood"
    capability: str              # 对应能力注册表的一项，如 "create_attack_flow"
    inputs: dict[str, Any]       # 参数值：常量 或 Ref（依赖）
    outputs: list[str]           # 本步产出的变量名，供后续 Ref 引用
```

`TestPlan = list[PlanStep]`。混合攻击的"并发"在此表达为 **fan-in**：多个攻击/业务 profile 配置步，最后汇入一个 `run` 步（`run` 的 inputs 引用前面各步产出的 `profile_id`）。

**示例（UDP flood + HTTP GET flood 混合，攻击 1Gbps / 200s）：**

```python
plan = [
  PlanStep("login",                    "login", {}, ["session_id"]),
  PlanStep("reserve_port",             "reserve_port", {}, ["port_id"]),
  PlanStep("create_flow_udp",          "create_attack_flow",
           {"attack_type": "udp_flood", "bandwidth_mbps": 500, "target": {"dest_ip": "11.0.0.1/24"}, "session_id": Ref("login","session_id")},
           ["flow_id_udp"]),
  PlanStep("create_flow_http",         "create_attack_flow",
           {"attack_type": "http_get_flood", "bandwidth_mbps": 500, "target": {"url": "http://x/index.html"}, "session_id": Ref("login","session_id")},
           ["flow_id_http"]),
  PlanStep("create_business",          "create_business_profile",
           {"bandwidth_mbps": 2000, "session_id": Ref("login","session_id")},
           ["business_profile_id"]),
  PlanStep("build_testcase",           "build_testcase",
           {"attacks": [Ref("create_flow_udp","flow_id_udp"), Ref("create_flow_http","flow_id_http")],
            "business": Ref("create_business","business_profile_id"),
            "duration_sec": 200, "port_id": Ref("reserve_port","port_id")},
           ["testcase_id"]),
  PlanStep("run",                      "run_testcase",
           {"testcase_id": Ref("build_testcase","testcase_id")}, []),
  PlanStep("stats",                    "get_stats",
           {"testcase_id": Ref("build_testcase","testcase_id")}, []),
  PlanStep("logout",                   "logout", {}, []),
]
```

## 5. 能力注册表（Capability Registry）

这是系统的"可执行知识库"，把每类操作绑定到一段**经过验证的代码模板**。每项能力：

```python
@dataclass(frozen=True)
class Capability:
    name: str              # "create_attack_flow"
    api_path: str          # 对应信而泰 API，如 "/v1/cl/ddos/attack/flow/create"
    client_method: str     # 稳定层方法，如 "AlpsClient.save_testcase"
    input_schema: dict     # 参数 schema（用于校验）
    output_fields: list[str]
    code_template: str     # Jinja2 模板，渲染出本步调用代码
```

能力分三类：
- **会话类**：`login` / `logout`
- **资源类**：`reserve_port` / `fetch_network` / `list_component`
- **配置与执行类**：`create_attack_flow` / `create_attack_profile` / `create_business_profile` / `build_testcase` / `save_testcase` / `run_testcase` / `get_stats`

注册表 = 代码模板 + 元数据，是稳定层 SDK 的"编排面"。它是**手写维护**的资产，LLM 只从注册表里**选**，不生成模板。

## 6. 各模块设计

### ① 需求解析层
- `docx` 用 python-docx 按标题层级拆分（复用现有 `utils/split.py` 的思路），产出若干"需求条目"。
- `intent.txt` 每行作为一条意图。
- 每条条目用 **LLM + Pydantic schema** 抽取成 `TestRequirement`（`model_validate_json(strict=True)`）。
- 攻击类型归一化：映射到已知攻击类型集合（复用 `utils/is_ddos.py` / `known_xinertel_attacks.md` 的 78 种）。

### ② 意图理解层（文档 → TestPlan）
这是最"智能"的一层，分三步，LLM 与确定性逻辑混合：
1. **检索**：对每种攻击类型，用 RAG（FAISS→CrossEncoder→LLM）在**能力注册表**里检索匹配的能力（如 `udp_flood` → `create_attack_flow`）。检索目标从"API 描述"升级为"能力模板"。
2. **编排**：LLM 依据结构化需求 + 检索到的能力，产出 `TestPlan`（步骤序列 + 依赖）。约束：步骤必须来自注册表、依赖必须指向已存在的产出字段。
3. **参数填充**：LLM 把需求里的数值/目标填进每步 inputs；带宽等"算出来"的量由确定性代码注入，覆盖 LLM 填值。

### ③ 校验（意图理解之后、代码合成之前）
- `TestPlan` 用 Pydantic 严格校验；
- 依赖闭环校验：每个 `Ref(step, field)` 的 `step` 必须在前、`field` 必须在其 `outputs` 中；
- 失败即回炉：把校验错误作为反馈，让 LLM 修正 `TestPlan`（带重试上限）。

### ④ 代码合成层（确定性）

- 输入 `TestPlan` → 渲染 `generated_xxx.py`：
  - 固定头：`from examples.sdk import AlpsClient`、`from models.ddos_attack_config import ...`
  - `main()` 或 `__main__`：实例化 `AlpsClient` → `login` → 按 `TestPlan` 顺序渲染每步调用 → `stats` 打印 → `finally: logout`
- 每个 `PlanStep` 用对应 `Capability.code_template` 渲染，`inputs` 里的 `Ref` 替换成变量访问，常量直接内联。
- 骨架、异常处理、`finally` 都是模板，LLM 不参与。

### ⑤ 校验与执行层（代码合成之后）

1. **静态**：`ast.parse` 语法检查 + 变量/依赖静态分析（所有 `Ref` 已消解）。
2. **执行**：在 **mock 环境**（伪造 `AlpsClient`，记录调用序列与参数）或**真实测试仪**上运行生成脚本。
   - mock：验证"调用顺序正确、参数正确、依赖已传递"，秒级、无副作用。
   - 真实：最终验收，跑通 = 成功。
3. 执行失败 → 把错误/断言反馈回意图理解层，重试修正。

## 7. 端到端示例

输入 `intent.txt` 一行：
```
测试 udp flood 和 HTTP get flood 的混合攻击，攻击总带宽 1Gbps，业务总带宽 2Gbps，时长 200 秒
```

产出（示意，生成脚本的骨架）：

```python
from examples.sdk import AlpsClient
from models.ddos_attack_config import TestcaseInfo, AttackModule, DataRate, ...

def main():
    client = AlpsClient(base_url=BASE_URL, name=NAME, password=PASSWORD, verify=False)
    try:
        client.login()
        port_id = client.reserve_port()               # 预留端口
        udp_flow  = client.create_attack_flow("udp_flood",  bandwidth_mbps=500, target={"dest_ip": "11.0.0.1/24"})
        http_flow = client.create_attack_flow("http_get_flood", bandwidth_mbps=500, target={"url": "http://x/index.html"})
        biz = client.create_business_profile(bandwidth_mbps=2000)
        tc_id = client.build_testcase(attacks=[udp_flow, http_flow], business=biz, duration_sec=200, port_id=port_id)
        client.run_testcase(tc_id)
        client.get_stats(tc_id)
    finally:
        client.logout()

if __name__ == "__main__":
    main()
```

> 500Mbps 是 `1000 // 2` 由代码算出，`duration_sec=200` 来自需求，`session_id` 由 `AlpsClient` 内部自持，无需显式传递——稳定层屏蔽了这些细节。

## 8. 与旧方案的本质差异（一句话对照）

| 维度 | 旧方案 | 本方案 |
|------|--------|--------|
| 输出 | JSON 用例描述 | 可执行 Python 代码 |
| 验证 | 靠人看 / 无 | 直接运行，跑通即通过 |
| 编排 | 固定模板流水线 | 需求驱动的 `TestPlan` IR，支持并发 fan-in |
| LLM 角色 | 全程生成（含"算数"） | 只做理解与编排，算数/校验/渲染由代码 |
| 可靠性 | LLM 写自由 JSON | 稳定 SDK + 模板化生成，LLM 不碰骨架 |

## 9. 分阶段实施计划

1. **P0 稳定层收口**：把 `AlpsClient` + `models/ddos_attack_config.py` 固化为可导入的稳定 SDK（`examples/sdk/`），补齐缺的 `run_testcase`/`reserve_port` 等方法。
2. **P0 能力注册表**：梳理 8~10 个核心能力（login/logout/reserve/flow/profile/business/build/run/stats），每项写好代码模板 + 参数 schema。
3. **P1 需求解析**：docx 拆分 + intent 解析 → `TestRequirement`（LLM + strict schema）。
4. **P1 意图理解 + 校验**：检索 + 编排 + 参数填充 → `TestPlan`，加依赖闭环校验与回炉重试。
5. **P2 代码合成 + 静态/执行校验**：模板渲染 + `ast` 检查 + mock 执行，闭环到修正。
6. **P2 评测基线**：可执行率、API 命中率、参数依赖正确率，作为回归指标。

## 10. 风险与对策

| 风险 | 对策 |
|------|------|
| LLM 编排出非法 `TestPlan` | 严格 schema + 依赖闭环校验 + 重试回炉 |
| 生成代码运行时参数类型/缺字段 | 稳定层 SDK 内做参数校验与默认值；mock 先跑 |
| 能力注册表覆盖不全（503 API） | 先覆盖高频 8~10 能力，其余按需增量补模板 |
| 真实测试仪不可用时的验收 | mock 执行 + 调用序列断言作为常绿回归 |
